## 1. 数据工程师应当交付什么

目标是让每个判断都能回答：**哪家企业的哪个业务单元，在什么时间，由哪些证据支持，适合采购、合作还是继续调查？**

采集结果应包含原始文档、可追溯事实、主体/角色关系、项目事件和评价时点快照。
不以网页数量、文本长度或命中关键词数量作为最终质量标准。

首版最小闭环为：

1. 确认企业、工厂、集团及项目对应关系，避免同名与错配。
2. 找到与产品作用场景有关的真实业务事实。
3. 查找当前采购/建设/替换窗口，并追踪更正、中标、终止等后续事件。
4. 提取预算和技术条件，同时保留口径、适用范围与未知项。
5. 将每项结论连接到来源、原文位置、时间和版本。
6. 为没有发现信息的企业保留采集状态，不能直接填“无需求”。

**公开数据负责提供线索和证据；内部授权业务数据负责补充接触、转化、成本与回款。**
仅靠公开网页，通常无法得到经过核验的采购决策权、真实可用预算、赢单率和交付毛利。

## 2. 先拿到产品侧配置，再安排企业采集

没有产品的使用场景、必要条件和商业边界，就难以判断哪些企业信息值得获取。
产品配置由产品/行业负责人维护，采集开发不自行臆造。

| 产品字段 | 说明 | 对采集的影响 |
|---|---|---|
| `product_id / product_version` | 稳定标识和版本 | 使查询、字段及评价可复现 |
| `use_cases / pain_points` | 解决的场景与问题 | 决定需要寻找的事实和关键词 |
| `buyer_roles` | 使用方、付款方、代理、渠道、集成商等 | 避免把同类产品卖方简单当作买方 |
| `target_processes / asset_types` | 工艺、设备或业务系统 | 支撑场景适配，而非只看工商行业 |
| `hard_requirements` | 技术接口、资质、部署条件等真正必要条件 | 必须寻找明确证据；未知不能当不满足 |
| `commercial_scope` | 服务区域、价格模式、订单下限、交付边界 | 决定是否需要采集距离、站点和实施复杂度 |
| `keywords / synonyms / exclusions` | 场景、工艺、需求、角色及歧义词 | 生成来源与产品对应的检索计划 |
| `opportunity_window` | 关注的未来周期与历史背景窗口 | 决定公告和事件回溯范围 |
| `priority_questions` | 最影响判断的未知项 | 决定有限采集预算的分配 |

“过去 12 个月”不是所有产品的统一规则：设备替换可能要查数年前合同，正在投标的项目则需要最新更正。
排除词仅用于降噪或标记，未经验证不直接永久排除企业。

示例配置，全部为说明性内容：

```json
{
  "product_id": "DEMO-PHM",
  "product_version": "v1",
  "use_cases": ["旋转设备故障预警", "减少非计划停机"],
  "buyer_roles": ["end_user", "oem", "integrator"],
  "asset_types": ["风机", "泵", "压缩机"],
  "keywords": {
    "need": ["预测性维护", "状态监测", "设备健康", "故障诊断"],
    "process": ["炼铁", "轧钢", "化工装置"],
    "buying": ["采购", "询价", "招标", "技改", "试点"],
    "seller_context": ["产品销售", "解决方案供应商", "案例客户"]
  },
  "hard_requirements": [],
  "window_policy": {
    "active_opportunities_months": 12,
    "historical_contracts_years": 5
  }
}
```

该示例没有替业务方设定强制设备数量、预算或资质门槛。

## 3. 从论证问题反推数据

每个事实要说明能支持哪一个论点，以及不能据此推出什么。

| 需要回答的问题 | 首要采集事实 | 较强论据 | 常见弱信号/误读 | 最重要的补证 |
|---|---|---|---|---|
| 它是谁，具体评估哪个主体？ | 登记标识、曾用名、所属集团、工厂/项目 | 一致的登记信息与项目主体对应 | 公司名相似就合并 | 工商主体、项目采购人或工厂地址 |
| 产品是否有用武之地？ | 实际主营业务、工艺、设备、系统、场景 | 有主体范围的技术文件、生产资料 | 工商经营范围宽泛即认为有需求 | 现场资产、技术条件与现有方案 |
| 是否存在明确痛点？ | 故障、能耗、产能、质量、人工或合规改造问题 | 采购技术要求、项目文件、授权访谈 | 新闻出现“数字化”即确认痛点 | 痛点程度、业务影响及时间 |
| 现在是否能推进采购？ | 意向、招标、询价、截止日、项目阶段 | 当前有效且角色明确的采购文件 | 多年前中标公告算作当前采购 | 最新更正、终止、中标与合同 |
| 有无与本产品有关的预算？ | 项目/标段预算、品类金额、审批状态 | 对应标段的预算/最高限价及来源 | 注册资本、集团营收、园区总投资当作预算 | 可采购范围与成本归属 |
| 谁使用、谁采购、谁付款？ | 采购人、代理、使用工厂、签约方、业务部门 | 公告明确角色、合同或授权 CRM 确认 | 联系人是代理就当成企业决策人 | 授权路径与真实业务部门 |
| 能否进入，有何替换阻力？ | 现有品牌、合同期限、准入、接口、服务要求 | 采购文件、合同、供应商准入说明 | 有现有供应商就判为无价值 | 到期、替换条件、组件合作机会 |
| 能带来多少经济贡献？ | 品类规模、报价、实施、服务、回款与售前成本 | 授权报价、成本台账、成熟订单结果 | 将项目总金额直接当成自身可得收入 | 条件客单价、交付边界及归因 |
| 是否有渠道或供应链价值？ | 真实供应、客户、代理、集成和集团关系 | 可定位主体与时间的双方/交易材料 | 企业声称“服务头部客户”就建立客户边 | 项目、关系方向和独立佐证 |

## 4. 采集优先级和字段字典

P0 为首版可用证据链所必需，P1 为提升商机判断所需，P2 为后续经济与供应链深化。
优先级是开发顺序，不代表允许编造未公开字段。

### 4.1 主体、经营与站点

| 字段 | 类型/口径 | 优先级 | 处理规则 |
|---|---|---|---|
| `entity_id` | 内部稳定字符串 ID | P0 | 不以企业名称哈希作为唯一身份 |
| `registry_id / registry_jurisdiction` | 登记标识与司法辖区 | P0 | 缺失可为空；保留标识类型与校验状态 |
| `legal_name / aliases` | 法定名、曾用名、简称及有效期 | P0 | 保留原文、来源和别名适用时间 |
| `entity_type / registration_status` | 主体类型、登记状态 | P0 | 不凭“研究”“大学”等单词认定商业属性 |
| `official_domains` | 域名及与主体关联的依据 | P0 | 集团站、子公司站和代理站分别标记 |
| `group_id / parent_entity_id` | 集团、母子公司关系 | P0 | 关系有来源、有效期；不将集团等同于采购主体 |
| `site_id / site_address` | 工厂、基地、经营站点 | P0 | 注册地址与生产地址分开 |
| `business_segments` | 实际主营业务和产品线 | P0 | 区别工商经营范围和实际经营 |
| `industry_code / taxonomy_version` | 行业代码与词表版本 | P1 | 保留原始行业描述，不以代码替代场景证据 |
| `employees / scale` | 人数、口径和报告期 | P1 | 区分集团/母公司/工厂，不把历史人数当当前值 |
| `operating_status` | 生产/建设/停工等及证据时间 | P1 | 与登记存续状态分别存储 |

### 4.2 项目、采购与采购能力

| 字段 | 类型/口径 | 优先级 | 处理规则 |
|---|---|---|---|
| `project_id / lot_id` | 内部 ID、来源项目号、标段号 | P0 | 标段分开，跨来源映射有匹配依据 |
| `project_name / category` | 项目名、采购品类 | P0 | 长标题不代替正文与附件解析 |
| `buyer_id / end_user_id / agent_id` | 采购人、使用方、采购代理 | P0 | 每种角色单独关联实体；未知为空 |
| `event_type / event_status` | 意向、公告、更正、结果、合同等 | P0 | 记录事件历史，不仅保存最新字符串 |
| `deadline / expected_purchase_period` | 精确截止时刻或计划月份/区间 | P0 | 月份不能伪装成某天精确时刻 |
| `requirements` | 产品类别、数量、技术、接口、部署 | P0 | 关联原文位置和适用标段 |
| `budget / ceiling_price` | 预算、最高限价 | P0 | 数值、币种、原单位、含税、范围分别保存 |
| `award_amount / contract_amount` | 中标、合同金额 | P1 | 不混成预算；不默认等于最终回款 |
| `awardee_id / existing_supplier` | 中标方或有证据的在用供应方 | P1 | 获奖、案例推荐不等同于在用供应商 |
| `contract_period / warranty_period` | 合同和质保起止/期限 | P1 | 到期不自动代表重新采购 |
| `qualification_requirements` | 投标/供应商准入要求 | P1 | 明确是硬要求还是优选项 |
| `payment_terms / acceptance_terms` | 付款、验收、质保、运维约束 | P1 | 按标段及合同版本保存 |
| `public_business_contact` | 公开业务部门、机构电话/邮箱 | P1 | 标明采购人或代理；不默认其拥有决策权 |

采购意向只是初步安排，需求、金额和时间应继续跟踪正式文件及后续变更。
这一解释可由[中国政府采购网的意向公开说明](https://www.ccgp.gov.cn/zcfg/mof/202003/t20200310_13982872.htm)核对。

### 4.3 场景、财务、供应链和内部结果

| 字段 | 类型/口径 | 优先级 | 处理规则 |
|---|---|---|---|
| `process / asset_type / asset_count` | 工艺、设备类型、数量及站点范围 | P1 | 不把设计能力当实际投产或满负荷运行 |
| `production_capacity` | 设计/在建/投产产能、单位及期间 | P1 | 三者分开，不能直接相加 |
| `pain_point / business_impact` | 痛点、停机/质量/能耗等影响 | P1 | 直接证据与行业推断分开 |
| `expansion / renovation / replacement` | 扩产、技改、替换事件 | P1 | 批复、开工、投产不是同一个阶段 |
| `installed_system / interface` | 在用设备/软件、协议与集成要求 | P1 | 招标要求不自动代表已部署 |
| `revenue / operating_cash_flow / capex` | 报告期、合并/单体、币种和审计口径 | P1 | 只反映相应口径；非上市企业公开缺失很常见 |
| `relationship_edges` | 供应/客户/代理/集成/归属关系 | P1 | 方向、品类、有效期、证据缺一不可 |
| `credit_or_delivery_events` | 与履约/交付有关的具体事件 | P2 | 标记状态、适用主体和更新，不用单条舆情一票否决 |
| `quote / delivery_cost / presales_cost` | 自身报价、可变成本和售前投入 | P2 | 来自授权内部系统；公开注册资本不可替代 |
| `crm_stage / action / mature_outcome` | 接触、阶段、结果及成熟状态 | P2 | 与结果标签隔离，避免混入历史输入 |
| `cash_received / net_contribution` | 回款、对应成本、订单和期间 | P2 | 内部账务/业务对齐，避免集团或渠道重复归因 |

## 5. 数据来源清单与接入选择

下表是来源登记起点，不表示这些网站已授权批量采集或本项目已验证接口稳定性。
官方入口核对日期为 2026-10-20；实际字段以目标页面与附件为准。

| 来源 ID | 来源/入口 | 适合获取 | 局限与接入要求 |
|---|---|---|---|
| SRC-01 | [国家企业信用信息公示系统](https://www.gsxt.gov.cn/) | 登记身份、名称和状态等主体核验 | 本次工具未读取到首页正文；查询/批量条件须单独确认，不能假设有公开 API |
| SRC-02 | 企业官网、官方公告/产品页/供应商门户 | 主营、基地、方案、准入、企业自有采购 | 官网身份需核验；案例和宣传需保留“企业自述”属性 |
| SRC-03 | [中国政府采购网](https://www.ccgp.gov.cn/)及地方分网 | 政府采购意向、公告、合同及变更等 | 覆盖政府采购，不代表全部民营采购；正文与附件一起处理 |
| SRC-04 | [全国公共资源交易平台](https://www.ggzy.gov.cn/)及交易平台列表 | 采购/工程项目、结果、变更和地方来源发现 | 可能汇集转载；同公告多站出现要归并来源链 |
| SRC-05 | 企业、集团或行业电子采购平台 | 询价、供应商入库、企业采购、合同信息 | 区分公开公告和授权登录内容；不默认平台提供批量 API |
| SRC-06 | [巨潮资讯](https://www.cninfo.com.cn/)、[上交所公开披露](https://www.sse.com.cn/) | 年报、主营、基地、财务、投资和合同披露 | 覆盖披露主体；合并财报不直接代表某工厂预算 |
| SRC-07 | 地方政府、园区、发改和生态环境部门公开栏目 | 建设、技改、环评、批复、开工或投产线索 | 每个地方栏目独立登记；阶段与项目编号须保留 |
| SRC-08 | [全国排污许可证管理信息平台公开端](https://permit.mee.gov.cn/) | 许可主体、生产场所、行业及相关公开材料 | 适用相应行业；许可记录不直接证明当前生产和采购；本次直接打开遇到验证页 |
| SRC-09 | [工信部数字化转型平台](https://szgx.miit.gov.cn/)与官方项目名单 | 数字化、智能工厂等场景与建设线索 | 入选/示范不等于新增采购预算；名单年度和项目主体要保存 |
| SRC-10 | 原创行业媒体、企业公开招聘、合作方公开案例 | 痛点、工艺、系统和关系线索补充 | 属于待核验线索；招聘人数、技能要求不能直接转成预算 |
| SRC-11 | 授权企业数据供应商 | 身份映射、覆盖补齐、授权关系与经营信息 | 记录许可证/合同范围、字段来源及时间，不把聚合标签当事实 |
| SRC-12 | 授权 CRM、报价、交付、服务及回款系统 | 真需求、采购角色、过程、成本、赢单和回款 | 非网页爬取任务；必须区分历史输入和之后发生的标签 |

全国公共资源交易平台的[平台介绍](https://www.ggzy.gov.cn/platform/platform.html)和巨潮资讯的
[官网介绍](https://www.cninfo.com.cn/)可用于核对渠道定位。
排污平台用途可另核对[生态环境部的官方说明](https://www.mee.gov.cn/ywgz/pwxkgl/gldt/201703/t20170324_408761.shtml)。

海外扩展时沿用同一契约，增加司法辖区及当地实体标识；例如美国披露主体可参考
[SEC EDGAR 官方数据接入说明](https://www.sec.gov/search-filings/edgar-search-assistance/accessing-edgar-data)。
不要要求所有境外企业具有中国登记标识，也不要把美国披露覆盖等同于全球公司覆盖。

### 5.1 来源登记必须先于大规模任务

每个来源配置至少记录：

```text
source_id / domain / publisher / source_type / jurisdiction
coverage_scope / document_types / original_or_aggregator
access_method / access_status / access_basis / reviewed_at
discovery_method / pagination_rule / attachment_rule / document_id_rule
date_and_timezone_rule / amount_rule / parser_version
rate_and_concurrency_policy / retry_policy / refresh_policy
last_success_at / backfill_watermark / replay_window
retention_policy / owner / known_limitations
```

优先使用已允许的数据接口、订阅、批量文件或授权导出，再选择允许采集的公开页面。
将来源条款、访问方式和 robots 规则纳入接入配置，robots 解析参考
[RFC 9309](https://www.rfc-editor.org/rfc/rfc9309.html)。
401/403、验证码、登录要求应标为访问受限，转授权接口、人工核验或暂缓接入，不通过反复换身份规避。
联系人默认只采公开业务部门/机构联系方式或授权 CRM 数据，私人联系方式不作为默认抓取字段。

## 6. 检索与发现：先发现文档，再抽取事实

### 6.1 为每个产品维护四组查询词

| 词组 | 示例 | 用途 |
|---|---|---|
| 场景/工艺/设备 | 旋转设备、压缩机、产线、锅炉；具体产品另配 | 补足行业标签过粗的问题 |
| 痛点/目标 | 停机、故障、能耗、良率、巡检、可靠性 | 找到未使用标准产品名的需求 |
| 采购/项目动作 | 采购、询价、招标、技改、新建、扩产、试点 | 区分意向和一般宣传 |
| 角色与状态 | 采购人、代理、中标、终止、更正、验收、供应商 | 识别参与角色和事件生命周期 |

查询模板可从下列组合开始，具体搜索语法按来源支持情况配置：

```text
企业法定名/曾用名 + 产品同义词 + 采购/询价/技改
集团名 + 工厂名/所在地 + 工艺/设备 + 项目/招标
项目编号 + 标段编号 + 更正/终止/中标/合同
企业名 + 基地/产线/资产 + 建设/投产/改造
企业名 + 供应商准入/采购平台/服务要求
```

企业名只作为查找线索，不足以确认文档归属。
搜索结果页和摘要只用于发现详情页；未获取原文的内容标为 `discovery_only`，不进入已核验事实层。

### 6.2 大规模采集采用来源增量流与企业补证结合

不要对 10 万家公司逐一重复搜索所有平台、反复下载相同 PDF。
优先按来源公告流/栏目增量发现文档，解析后用主体标识、别名和项目号关联企业。
企业定向查询用于身份核验、补缺、追踪高价值项目和审计排除集。

| 档案层 | 处理对象示例 | 采集深度 |
|---|---|---|
| L0，基础覆盖 | 全库企业 | 身份、行业/主营、官方站点、工厂与来源覆盖状态 |
| L1，机会发现 | 公告流命中及行业候选 | 采购事件、项目、时间、角色、正文与附件 |
| L2，重点补证 | 精评候选与高不确定对象 | 技术、预算口径、采购进展、准入与在用方案 |
| L3，人工/授权验证 | 待推进客户和项目 | 真实需求、角色确认、报价、交付和成本 |

例如“全库 10 万、召回 5,000、精评 500、推进 100”可以作为预算规划，不能变成永远只采高分企业的封闭循环。
保留按行业、资料完整度及未入选企业分层的采集审计样本，并记录抽样策略。

## 7. 主体与供应链角色识别

### 7.1 实体归并规则

1. 优先使用与辖区匹配、经过校验的登记标识；名称、地址和官网作为辅助证据。
2. 没有稳定标识时生成临时内部 ID，保存候选匹配和 `unresolved` 状态，不强行合并。
3. 集团、法人、分公司、工厂和项目分别建 ID，并用有时间和证据的关系连接。
4. 简称和曾用名保留有效期；“某集团采购中心”不自动等于所有子公司共同采购。
5. 许可证号、股票代码、招标项目号和登记标识分列，不截取后拼凑成同一主键。
6. 模糊名称匹配只能提出待确认关联；高影响主体错配进入复核队列。

### 7.2 角色按事件或产品关联，允许一企多角色

| 角色 | 含义 | 可依赖证据 |
|---|---|---|
| `end_user` | 方案最终使用企业/工厂 | 技术文件、交付地址、使用单位 |
| `buyer` | 正式采购主体 | 公告采购人、合同签约范围 |
| `payer` | 支付责任方 | 合同/授权业务记录；不明确则未知 |
| `agent` | 招标/采购代理 | 公告角色栏目；不能据其电话推断买方决策人 |
| `supplier / oem` | 产品/设备/组件供应方 | 中标、合同、供货材料 |
| `integrator / distributor` | 集成或渠道合作方 | 授权、合作、联合交付或分销材料 |
| `influencer` | 技术规范或采购选型影响方 | 项目职责或授权业务记录 |

中标方通常是该事件的供应方，不因为中标金额较高就被当成该产品的采购方。
供应方仍可能采购组件、升级自身系统或成为渠道，其价值要按合作路径另外判断。
年报中的匿名客户、模糊的“头部客户”和展示 logo，不能靠猜测绑定成真实客户关系。

## 8. 采购事件和项目必须持续追踪

至少保留以下事件类型，原始公告类型同时保存：

```text
intent / notice / clarification / amendment / deadline_extension
award / contract / acceptance / cancellation / termination / unknown
```

这是事件类型集合，不是所有来源都遵守的严格单向状态机。
不同标段可有不同状态；更正、撤销、重新招标、流标后重启要记录关系，而不是简单覆盖旧记录。

| 情况 | 处理规则 |
|---|---|
| 招标截止已过、无后续结果 | 标记“截止已过、结果未知”，不自动视为成交、终止或仍可投标 |
| 采购意向 | 保留计划月份、品类与金额；继续追踪正式文件 |
| 更正延长截止 | 关联被更正事件和标段，按有效版本重建当前截止日 |
| 中标/签约 | 对应当前标段阶段推进；不能继续宣传为同一轮开放采购 |
| 终止/取消/废标 | 保留原因、范围和后续；新一轮采购另建或显式关联 |
| 验收/交付 | 代表该记录覆盖范围内的履约进展，不等于未来永无需求 |
| 公告被删除/详情返回 404 | 记录抓取状态；没有撤回证据时不推断项目取消 |

项目关联优先使用来源项目号、标段和正式更正引用，再辅以采购主体、名称、地点和时间。
来源间编号体系不同、名称相似且无法确认时，保留待确认，不强行拼接完整生命周期。

## 9. 证据、时间、金额与冲突契约

### 9.1 每条可用事实都要有证据定位

| 字段 | 要求 |
|---|---|
| `claim_id / claim_type` | 一项可检验的事实，如某标段预算或某工厂使用某设备 |
| `assessment_question_ids` | 支持的评估问题，如场景适配、需求、时机、预算或采购角色 |
| `subject_id / scope` | 明确法人、集团、工厂、项目或标段范围 |
| `value_raw / value_normalized` | 原始值和标准值同时保存 |
| `claim_state` | `supported / refuted / unknown / conflicting`，不等同于模型置信度 |
| `attribution` | 官方公告、企业自述、合作方自述、媒体转述、内部确认等 |
| `evidence_refs` | `document_version_id + 页/段落/表格/单元格/坐标 + 原文片段` |
| `source_id / canonical_url` | 原始渠道与详情 URL；转载另存传播链 |
| `extraction_method / version` | 规则、OCR、模型或人工，及其版本 |
| `extraction_confidence / review_status` | 抽取质量与复核状态，不当成事实为真的概率 |
| `contradiction_group / supersedes` | 互相冲突或被正式更正的事实关联 |

“有来源”不等于“结论已核验”：企业自己宣称降本 30%，应保存自述主体与适用案例，不能当成所有客户的实际效果。
没有采集到预算时保存未知及原因，不创建“预算为 0”的事实。

### 9.2 分开管理至少五种时间

| 时间 | 含义 |
|---|---|
| `event_at / event_period` | 事件真实发生时间，或能够支持的日期区间 |
| `published_at / published_on` | 来源发布时间；只有日期时不伪造时分秒 |
| `first_observed_at` | 系统第一次观察到该文档版本的时间 |
| `fetched_at / processed_at` | 本次抓取、处理的流水时间 |
| `valid_from / valid_until` | 事实/合同/许可或公告条件的适用期 |

每种时间记录精度、时区和原文；“2026 年第四季度”保留为区间。
保守在线回放只允许使用 `first_observed_at <= as_of` 的版本。
如需按历史公开时间重建研究样本，必须另有能证明当时版本存在的来源/存档依据，并标记不同回测口径；
不能用今天抓到的、标着早期日期的更新正文，直接假装系统过去已经知道全部内容。

### 9.3 金额必须保留语义和范围

分别存储预算、最高限价、中标额、合同额、实际回款；
同时记录 `amount_raw / decimal_value / currency / unit / tax_basis / amount_scope / period / is_range`。
例如“580 万元”可以标准化为 `5800000 CNY`，但要保留原文单位。
“不超过”“约”“至少”及金额区间不能被压成伪精确点值。

集团营收不是子公司可用现金；园区总投资不是当前标段预算；
整线采购金额不是本产品可得收入；中标总额不是客户已付款金额。
抽取成功但口径无法确定时保存 `scope_unknown`，不进入确定预算特征。

### 9.4 多来源与冲突

同一公告的转载、搜索缓存、同一通稿多站出现，应归入同一来源家族，不累计为多份独立佐证。
财报、官方公告、企业网站的适用范围不同，不用“权威源优先”简单覆盖所有差异。
显式更正可替代其指明的旧事实；不明确的矛盾保留双方记录并进入复核。
不同年份、不同工厂或集团/单体口径的数值差异不一定构成冲突。

## 10. 采集与处理流水线

### 10.1 分层保存，允许回放和重新抽取

| 层 | 交付对象 | 必须保留的内容 |
|---|---|---|
| 来源登记 | `source_registry` | 来源、覆盖范围、访问方式、允许范围、解析和调度规则 |
| 发现与抓取 | `fetch_log` | 查询/栏目、页码或游标、目标 URL、状态、时间、重试、失败原因 |
| 原始层 | `documents / document_versions` | 来源文档 ID、URL、原始 HTML/PDF/附件、字节哈希、观察时间、版本关系 |
| 文本层 | `document_segments` | 正文、页码、标题、表格与 OCR 定位，抽取方法版本 |
| 主体层 | `entities / entity_aliases / entity_links` | 企业、集团、工厂及项目映射、歧义和复核记录 |
| 事实层 | `claims / claim_evidence` | 类型化值、适用主体、证据定位、状态、时间及冲突 |
| 事件/关系层 | `events / event_links / relationship_edges` | 项目标段事件链、主体角色、供应链关系与证据 |
| 服务层 | `entity_product_snapshots` | 产品、评价时点、事实投影、覆盖缺口及全部依赖版本 |
| 反馈层 | `actions / outcomes` | 内部行动、成本和成熟结果，独立访问与时间边界 |

这些是建议逻辑对象，不要求第一版使用某一种数据库，也不要求每个对象独立部署服务。
关键是原始文档、抽取事实、推断和业务结果不互相覆盖。

### 10.2 建议处理顺序

1. 从来源目录、增量公告、站点订阅或授权文件发现文档；记录完整检索任务范围。
2. 获取详情和附件，识别内容类型；先保存原始字节与获取元数据，再进行抽取。
3. 检查 HTTP 状态和页面语义。HTTP 200 的验证码、登录页、错误页不是有效正文。
4. 解析标题、时间、主体、项目号、正文和表格；扫描 PDF 走 OCR，并保留坐标。
5. 归并主体，建立文档到企业/工厂/项目的多对多关联。
6. 按字段抽取明确值及支持片段；无法定位原文的模型输出不进入已核验事实。
7. 归一化金额、日期、地点、设备词和角色，保留原始值与归一化规则版本。
8. 建立事件关系、识别更正、去重与冲突；必要时进入复核队列。
9. 生成截至评价时点的产品相关快照，过滤未来结果和无权限字段。
10. 发布受影响实体/项目的更新事件，触发索引与评分档案刷新。

规则抽取适合明确的编号、日期和金额；复杂表格及角色可用模型辅助。
模型的角色是提出有位置依据的结构化候选，不是补写看起来合理的缺失事实。
外部页面里的指令文本只当作原始资料，不执行、不用于修改抽取规则。

### 10.3 文档去重与幂等

- 优先使用来源稳定文档 ID；查询 URL 中影响项目、标段或分页的参数不能盲目删除。
- 同文档 ID 的新内容形成新版本；原始字节 SHA-256 用于精确版本和重放校验。
- 清洗文本指纹可辅助发现转载/近重复，但不能据此丢弃具有更正、金额或截止日差异的版本。
- 正文与附件分别存文档版本，用父子关系连接。附件即使 URL 不变，也要按内容识别更新。
- 同一文件关联多家参与方时只存一份原始对象，但保留各主体角色和各条证据关联。
- 重跑任务不得增加相同来源版本的重复事实；抽取器版本变化允许重新处理，并保存前后版本关系。
- 原文确有多个采购数量或不同币种时，应保留多条范围明确的事实，而不是以单一字段后写覆盖前写。

## 11. 缺失、失败和覆盖状态

采集过程状态、字段缺失原因、事实真伪和项目状态是四种不同信息，不要合用一个 `status` 字段。

| 采集状态/原因示例 | 意义 | 禁止的解释 |
|---|---|---|
| `not_attempted` | 尚未安排该来源/字段 | 企业没有相关信息 |
| `fetched / extracted` | 已获取/完成抽取 | 所有事实都已核验 |
| `not_found_in_scope` | 在记录的来源、条件和期间内未找到 | 企业没有需求或从不采购 |
| `field_not_disclosed` | 文档可读但字段未披露 | 金额/设备数量为零 |
| `not_applicable` | 对该主体/产品不适用，有理由 | 采集失败 |
| `access_restricted / captcha` | 访问受限或验证页 | 搜索结果为零 |
| `timeout / source_error` | 网络/服务故障 | 企业不存在 |
| `parse_failed / ocr_low_quality` | 无法可靠解析 | 正文没有该事实 |
| `entity_unresolved` | 信息存在，主体尚未确认 | 随意绑定最相似企业 |
| `conflicting` | 多个可比较事实冲突 | 自动选最大金额或最新抓到的一条 |

每次 `not_found_in_scope` 必须附带来源、查询条件、时间范围、分页是否完整、访问是否成功。
不能只保存一句“全网未发现”。
抓取失败进入来源重试/人工队列，事实未知进入补证队列，不能两者都变成低分客户。

### 11.1 覆盖指标分开统计

至少交付：计划来源数、已成功访问数、已完整处理任务数、关键字段可用率、证据定位率、
主体已确认率、项目状态跟踪率、过期档案比例和复核积压。
“字段可用”须区分已披露、未知、不适用；`null` 的存在本身不代表质量差，也不能被随意填值消除。
来源访问率或 OCR 置信度不能直接命名为“企业价值置信度”。

## 12. 增量更新、时效和成本

### 12.1 初始调度建议

以下为待按来源允许条件、更新频度和预算调整的起始建议，不是网站承诺的访问速率或业务事实有效期：

| 数据 | 初始更新方式/周期 | 触发式优先处理 |
|---|---|---|
| 基础登记/别名/集团关系 | 30–90 天核对或订阅变更 | 主体变更、项目角色冲突 |
| 新公告发现 | 来源增量流每日检查 | 与当前产品/重点企业匹配的新公告 |
| 近期有效采购项目 | 允许时每 6–24 小时关注更正流 | 截止临近、金额/标段/资格改变 |
| 项目结果与合同 | 按来源发布流及项目定向跟踪 | 中标、更正、终止、合同/验收出现 |
| 建设/技改/工厂进展 | 7–30 天或事件订阅 | 开工、试产、投产和停工 |
| 财报/年度经营资料 | 新披露触发，避免重复下载同一版报告 | 更正报告、重大投资/合同披露 |
| 企业产品、案例和业务页面 | 7–30 天按内容变化抓取 | 产品角色、业务范围、供应商准入变化 |
| 内部 CRM/报价/回款 | 授权事件同步，并定期对账 | 阶段改变、动作执行、合同、收付款 |

高频监测应优先复用来源的更正/公告流，不对大量单企业页面无差别重复轮询。
支持 ETag/Last-Modified 的来源可条件请求；无变化时不重复 OCR 和模型抽取。
按内容变化、解析器版本变化和待补证问题分别触发处理，避免整个 10 万家全量重建。

### 12.2 回填与漏采处理

保存增量游标和成功处理水位，水位仅在相应批次落库成功后提交。
采用可配置的重叠回看窗口，补偿延迟发布、排序变化和更正旧公告；范围由来源行为验证决定。
定期比较已知项目的完整生命周期、列表与详情数量差异，并对断档来源做历史重放。
来源不可用时保留旧档案及 `stale/source_gap` 标记，不用新抓取时间掩盖内容已陈旧。

事实变更需关联受影响的企业、站点和项目，重新生成相应快照；
只是让 JEV 缓存过期，并不会自动刷新企业数据。

      "allocation_to_our_product": null
    },
    "claim_state": "supported",
    "attribution": "procurement_notice",
    "verification_status": "extracted_not_independently_confirmed",
    "evidence_refs": [{
      "document_version_id": "DEMO-DOC-V1",
      "source_url": "https://example.invalid/notice/DEMO-001",
      "location": {"page": 2, "section": "采购范围"},
      "quote": "一标段：设备状态监测及配套改造，预算人民币580万元。"

  "times": {
    "published_at": null,
    "published_on": "2026-10-12",

该记录仅能支持：某标段公告表达了设备监测相关采购和标段预算。
因为未检查后续公告，不能仅凭原截止日在未来就认定“当前可投标”；
也不能认定该企业给本产品准备了 580 万元预算。

| 论证节点 | 示例判断 | 下一步数据任务 |
|---|---|---|
| 主体 | 已有采购人和使用基地 ID | 核实基地与法人归属及代理角色 |
| 适配 | 标段范围包含监测，但还有配套改造 | 解析技术附件和分项清单 |
| 时机 | 原截止日未到，后续状态未核验 | 查更正、延期、终止及结果流 |
| 经济 | 只有整标段预算，产品份额未知 | 补品类数量、报价、实施和服务条件 |
| 行动 | 有理由进一步补证 | 技术和销售复核，不直接填高赢单率 |

## 14. 向当前 JevP 接口交付什么

当前接口主要接收 `name/basic/bidding/website/supply_chain`，并不自动完成上述主体、时间和证据校验。
适配层应负责生成已通过校验的产品相关快照，证据全文和结构化事实保留在数据仓库。

| 当前字段 | 建议投影 | 注意事项 |
|---|---|---|
| `name / id` | 已确认企业法定名与稳定内部 ID | 集团与工厂不应因同名而覆盖 |
| `basic` | 适用主体的主营、地区、规模及口径 | 不用集团数据伪装成单体数据 |
| `bidding` | 当前产品相关项目/标段摘要、时间、类型和证据 ID | 关联后续事件；不能把中标方当采购人 |
| `website.strategy/news` | 来源明确的业务、建设及经营事实摘要 | 保留“自述/已核验/未知”含义，不堆砌宣传词 |
| `supply_chain` | 已确认角色与关系路径的简要说明 | 真实关系留在关系层，不从摘要反推事实 |
| `version` | 快照/特征版本 | 当前哈希会受内容变化影响；数据刷新另由管线触发 |
| `embedding`，可选 | 同一嵌入模型版本生成的向量 | 模型版本在仓库/特征注册中约束；不能只校验维度 |

**待实现的适配契约：**`entity_id + product_version + as_of + evidence_snapshot + feature_schema_version`。
采用明确字段白名单，不把整个数据仓库对象直接塞进接口。
现有代码会把除 embedding 外的企业字段传入评分上下文，因此尤其要在适配层排除：
评价之后的成交/回款结果、人工金标准、旧模型评分、无权限字段及外部页面指令。
不能依赖模型自己识别哪些字段属于未来标签。

按产品和问题选择证据片段，在输入长度预算内保留原文引用、关键限制和未解决冲突。
记录纳入/遗漏的证据 ID 与 `truncation_reason`；不要按抓取顺序简单截取前若干字符。
原始文件不能因提示词长度限制而被丢弃。

建议另交付证据清单，支持结论反查：

```json
{
  "entity_id": "DEMO-ENTITY-001",
  "product_id": "DEMO-PHM",
  "as_of": "2026-10-20T12:00:00+08:00",
  "snapshot_version": "DEMO-SNAPSHOT-001",
  "evidence_ids_used": ["DEMO-CLAIM-001"],
  "unresolved_questions": ["最新项目状态", "技术适配", "产品对应预算份额"],
  "collection_coverage": {
    "official_identity": "pending_verification",
    "procurement_detail": "extracted",
    "procurement_followups": "not_attempted",
    "internal_crm": "not_available"
  },
  "excluded_fields_policy": "no_future_outcomes_or_existing_scores"
}
```

当前这份清单是数据工程交付设计，尚未作为新字段契约接入 API；不能把文档设计视为接口已实现能力。

## 15. 验收规范与反例集

### 15.1 首版必须通过的契约检查

- 每条用于正式评价的已支持/已反驳事实，均能定位原始文档版本、原文位置、主体范围及时间依据。
- 文档归属、角色或金额范围未确认时，显式保持未知/待复核，不用近似值填平缺口。
- `available_at` 若另行采用，必须说明与首次观察/历史可得证明的关系，不能无条件等同于发布日期。
- 相同来源版本重跑不增加重复事实，解析器升级后可回放并追溯差异。
- 生成给模型的历史快照不包含 as_of 之后才获得的资料和结果标签。
- 演示、测试记录和正式记录隔离，`is_synthetic=true` 不进入正式企业库。

这些是程序契约，应逐条检查；不能据此声称真实抽取准确率已达到 100%。

### 15.2 真实抽取质量另行抽样验证

按来源、文档类型、行业、语言和 OCR 情况分层抽样，重点核对：
实体匹配、买方/卖方/代理角色、项目/标段归并、状态、日期精度、金额单位/口径及证据支持关系。
关键高影响字段由双人独立标注并仲裁，报告错误类型、样本量与区间。
首批可从 100–300 份混合文档开始暴露规则缺陷；该规模是开发起点，不能自动证明目标精度。

| 必测反例 | 预期处理 |
|---|---|
| 同名不同地区或不同登记主体 | 不强行合并 |
| 集团大额投资与子公司采购混淆 | 分开主体和金额范围 |
| 中标方误当采购方 | 角色纠正，保留原事件 |
| 只有采购意向，没有正式公告 | 计划状态，继续跟踪 |
| 截止日期被延期/项目终止 | 应用相关有效更正，保留历史 |
| 合同已签，仍按当前开放招标输出 | 标明对应阶段，不制造当前投标窗口 |
| 200 状态实际为验证/登录页面 | 访问受限，不提取成正文 |
| 扫描件金额漏掉“万”或币种 | 复核/隔离，不能以原数字直接入预算 |
| 正文无金额但模型给出预算 | 不进入已核验事实 |
| 多站转载同一公告 | 一个来源家族，不累计独立佐证 |
| 匿名前五大客户或品牌 logo | 不猜具体客户关系 |
| 今天获取的旧日期更新正文 | 不直接作为过去已知版本 |
| 网站 404 或无搜索结果 | 记录访问/检索状态，不判企业无需求 |
| CRM 在评价后赢单 | 作为结果标签，不进入当时特征 |
| 公司是方案供应商但也可能集成合作 | 多角色记录，按产品与事件补证 |

## 16. 实施拆解与交付包

| 任务 | 负责人类型 | 交付物 | 主要依赖 |
|---|---|---|---|
| DATA-01，产品问题与词表 | 产品/行业负责人 | 产品配置、采购角色、必要条件和术语 | 业务目标确认 |
| DATA-02，来源接入登记 | 数据负责人/采集开发 | 来源覆盖、允许接入方式、解析与调度规则 | 渠道可访问性 |
| DATA-03，原始抓取与版本层 | 数据工程 | 文档、附件、哈希、抓取日志和重放 | DATA-02 |
| DATA-04，主体与项目归并 | 数据工程/行业复核 | 稳定 ID、别名、集团/工厂及标段映射 | DATA-03 |
| DATA-05，字段和证据抽取 | 抽取开发/行业复核 | 角色、金额、时间、技术条件与引用 | DATA-01、DATA-04 |
| DATA-06，事件链与冲突 | 数据工程 | 更正/终止/结果关系、未知与复核队列 | DATA-05 |
| DATA-07，快照与 JEV 投影 | 数据工程/算法 | as_of 快照、白名单、版本、覆盖清单 | DATA-05、DATA-06 |
| DATA-08，质量与来源监控 | 数据质量负责人 | 分层金标准、反例回归、失败和时效看板 | DATA-03 起持续进行 |
| DATA-09，增量与预算 | 数据工程 | 水位、回看、变化触发、重点补证和排除集审计 | DATA-06、DATA-08 |
| DATA-10，内部结果接入 | 销售运营/数据工程 | 授权 CRM、成本、阶段、回款和成熟标签 | 业务权限及口径对齐 |

第一轮建议选 1–2 个明确产品、100–300 家有不同角色的企业，覆盖官网、采购、经营披露和至少一种场景来源。
先完成从原文到判断的样本闭环，再按来源横向扩展；不以一开始抓满 10 万份长简介作为成功标准。

每次交付包至少包含：

```text
source_registry（接入与覆盖登记）
product_collection_config（产品问题与查询词版本）
document_manifest + raw_objects（原文/附件清单与访问依据）
entities + aliases + entity_links（主体及关系）
claims + claim_evidence（事实、口径、未知与引用）
events + event_links（项目/标段及生命周期）
snapshots + evidence_manifest（评价时点档案及证据清单）
fetch_failures + review_queue（失败、歧义与复核）
quality_report（抽样、分群错误、时效和缺口）
replay_instructions（重放、版本和增量更新说明）
```
