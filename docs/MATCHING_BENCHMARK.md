# 企业匹配优化：离线测试报告

日期：2026-10-20（Asia/Shanghai）。环境：Apple M4、16 GiB RAM、macOS arm64、Python 3.14.3。

**本报告仅包含离线合成测试，没有运行真实 LLM、GPU 推理或生产企业库。**
用户选择先完成离线验证。模型由确定性的 logprob fixture 替代，耗时只体现本地
档案处理、候选检索、评分协议、排序和缓存的开销；不能视为真实服务端到端延迟。

## 正确性与接口验证

`python -m pytest -q`：**116 passed**，其中原有 76 项、新增 40 项。
当前安装的 Starlette 测试客户端提示一条 httpx 弃用警告，不影响通过结果。
另通过 Python 编译检查、调试页 JavaScript 语法检查及 Git 空白检查。

覆盖产品影响模型输入和排名、demo 产品覆盖、分批与逐企业结果一致、提示词数量/字符预算、
本地 token 上限、缓存的 TTL/容量/持久化及产品/档案/日期/模型 revision/问题/规则变化失效、
重名企业对齐、单条故障隔离、无候选 token 证据不缓存、中文词项和外部向量召回、索引淘汰、
异步状态/进度/分页/队列背压/任务失败及参数校验。

HTTP 测试实际访问本机回环 HTTP 服务，跨两个同时调用的批次发送 18 个请求，
验证同一后端的最大同时请求数为 3（配置值），并验证结果顺序与 503 故障隔离。
回环响应由测试程序生成，没有调用外部模型。

## 四档规模

每个企业默认 core 3 问。Top-K 模式默认召回池 5,000、精评候选 500、返回前 100；
企业总数不足 500 时评价全部企业。
Top-K 耗时复用已构建索引、关闭评分缓存，重复 20 次；不含首次建索引、上传或网络。
全量与缓存耗时各为一次样本；单位均为毫秒。

| 企业数 | 首次建索引 ms | 全量评分 ms | Top-K P50 / P95 ms | 新评估题数：全量 → Top-K | 热缓存全量 ms |
|---:|---:|---:|---:|---:|---:|
| 100 | 1.21 | 5.04 | 4.13 / 4.29 | 300 → 300 | 1.82 |
| 1,000 | 10.79 | 41.81 | 21.52 / 22.07 | 3,000 → 1,500 | 18.04 |
| 10,000 | 110.70 | 436.57 | 25.61 / 28.67 | 30,000 → 1,500 | 188.35 |
| 100,000 | 1127.36 | 4511.97 | 48.43 / 49.39 | 300,000 → 1,500 | 2123.57 |

在 10 万家这组样本中，新评估题数从 300,000 降至 1,500，减少 99.5%（200 倍数量差）。
全量冷评分仍线性处理 10 万家；热缓存模型评估量为 0，但读取、排序、组装全量结果仍有开销。
该压测进程累计峰值 RSS 为约 609.7 MiB，包含档案、索引、全量结果、SQLite 缓存及运行时；
这是合成短档案的进程峰值，不是生产服务的内存容量保证。

## 质量和增量检查

- 四档合成数据的 Top-100 与全量评分重合率均为 1.0，NDCG@100 均为 1.0。
- 每档均检查前 100 家分批评分与逐企业评分完全一致。
- 热缓存四档均新增 0 次问题评估；仅更新一家档案，四档均仅重评 1 家。
- 合成标签由测试场景定义，评分 fixture 也按场景规则工作；100% 标签一致不代表真实模型准确率。
  数据包含买方、相似产品卖方和行业不相关企业，但不覆盖所有业务分布。

## 复现

```bash
python -m pip install -r requirements.txt
python -m pytest -q
python benchmarks/benchmark_matching.py --sizes 100,1000,10000,100000 --repeat 20 \
  --output results/matching_scale.json
```

[原始 JSON 数据](matching_benchmark.json) 保留所有测量字段。
真实模型验收仍需在实际部署硬件上测量 QPS、输入 token/s、P95、显存与失败率，
并用独立人工标签评估召回损失与排序质量。`topk` 不保证得到全库真实最优结果；
需要完整 JEV 分数时使用 `full`。

接口、缓存键和部署容量边界见 [性能说明](MATCHING_PERFORMANCE.md)。
